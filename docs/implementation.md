# Implementation: the Build, and What the Image Does So Far

`docs/project-state.md` is the working document and `docs/spec/` is the input.
This is the output side: how the image is built, what it currently does, and
which specification requirements it already meets.

## Building

```sh
cmake -B build -G Ninja -DCMAKE_TOOLCHAIN_FILE=cmake/toolchain-mipsel-ps2.cmake
ninja -C build
ninja -C build check
```

The toolchain is LLVM: `clang` assembles, `ld.lld` links each component at the
address it runs from, `llvm-objcopy` lifts the raw bytes back out, and
`tools/mkromdir.py` assembles those files into the archive of
`docs/spec/01-rom-archive.md`. There is no cross-gcc and no vendored toolchain.

The PS2 has two processors and one assembler serves both. `-march=mips3` is
what the *assembler accepts*, not a statement about who runs the code: the IOP
is an R3000A and its path must stay within MIPS I, and the reset dispatch both
processors execute must stay within what both have.

| Piece | Runs at | Source |
| --- | --- | --- |
| `RESET` | `0xBFC00000`, both CPUs | `src/boot/reset.S` |
| `RDRAM` | wherever the archive puts it | `src/boot/rdram.S` |
| `KERNEL` | copied to physical 0, entered at `0x80001000` | `src/kernel/*.S` |
| `IOPBOOT` | in place from the ROM window | `src/boot/iopboot.S` |
| `SYSMEM` | relocated to the boot list's base | `src/iop/sysmem.S` |
| `LOADCORE` | relocated after it | `src/iop/loadcore.S` |
| `EESYNC` | last in the boot list | `src/iop/eesync.S` |
| `ROMVER` | not executed | generated by `tools/mkromver.py` |

The kernel is four files, split by what the interface fixes rather than by
subject: `vectors.S` is the `0x1000`-byte vector page and the handlers EE-8f
requires to live inside it, `tables.S` the three dispatch tables at the
addresses EE-6f names, `syscall.S` the `Sys` entry, and `entry.S` the entry
point and its serial output. The link script is what puts each at its address;
nothing computes a layout at run time.

## What the image does today

**The EE boots into our kernel.**

```sh
python3 tools/eesim.py build/rom.bin
```

```
   CP0 at reset: Config=0x73003, Status=0x70400000, Count=0x0, Compare=0x1
   first TLB entry: index 0, EntryHi=0x70000000, EntryLo0=0x80000007, EntryLo1=0x00000007
   RDRAM called at 0x9fc023f0: True
   reached 0x80001000: True

the kernel's own console:
   # PS2BiosRebuild EE kernel: entered at 0x80001000.
```

That is `spec/04` EE-1, EE-1a, EE-1b, EE-2, EE-3b, EE-3d and EE-4 executed on
our own code rather than the reference's.

**The kernel serves syscalls.** `tools/eesim.py`'s harness calls into our
kernel the same way it called into the reference's:

```sh
python3 tools/eesim.py build/rom.bin --syscall 0x14 3
# syscall 0x14(0x3) -> 1 (0x00000001)
```

| Called | Result | Requirement |
| --- | --- | --- |
| `0x14`, twice | `1` then `0`, INTC mask bit set | EE-8g |
| `0x16` | DMAC bit `16 + n`, not `n` | EE-8g |
| `0x1A` | reaches `0x14`'s handler | EE-8c |
| `-0x14` | reaches `0x14`'s handler | EE-7b |
| `0x0D` | writes the exception table; out of range returns `0` | EE-6e |
| `0x74` | writes the syscall table | SYS-5a |
| `0x75` | returns, quietly | SYS-3b |
| an unimplemented slot | `# syscall not implemented: 0x21` | EE-8d, SYS-3a |

Every one of those returning at all is EE-7c: the handler advanced `EPC` past
the `syscall`, or control would come back to the same instruction forever.

**Two requirements from the reference's own gate.** `tools/eeksys.py --check`
judges a `KERNEL` file structurally, and ours now fails it on exactly two
counts, both "not written yet" rather than "written wrong":

```sh
python3 tools/romdir.py build/rom.bin --extract <outdir>
python3 tools/eeksys.py <outdir>/KERNEL --check
# EE-8d: ... also use the undefined reporter        (98 unimplemented slots)
# EE-8e: kseg1 slots [] != ['0x60', '0x61', '0x62'] (the cache trio)
```

The vector page, EE-5a's identical `0x000`/`0x180`, EE-6b's single common
handler, and EE-8a to EE-8c's slot count, absence of nulls and alias blocks all
pass already.

**The IOP reaches `IOPBOOT` and reads its boot list.**

```sh
python3 tools/iopsim.py build/rom.bin
# POST sequence: ['0xfc', '0x2', '0x3', '0x4', '0x5', '0x8', '0x9']
```

That is `spec/03` BOOT-5a's retail sequence, complete: the handoff of BOOT-6
resolved `IOPBOOT` by name and entered it with the RAM-size byte, and `IOPBOOT`
sized its stack from that byte (BOOT-7), resolved `IOPBTCONF` with its own copy
of the scan, and parsed the list (BOOT-9) — leaving the base address `0x800`
and a count of resolved names in low RAM where `tools/imgcheck.py` reads them.

**And it loads the first one.** `SYSMEM` is built as a real IRX — `tools/mkirx.py`
turns a linked ELF into the container of `spec/02` IRX-1 — and it passes the
same conformance checker the reference's modules do:

```sh
python3 tools/irxinfo.py build/sysmem.irx --check
# build/sysmem.irx: ok
```

`IOPBOOT` then copies its load segment to `0x800`, zeroes the bss behind it,
applies the fixups of IRX-3 and calls the entry with a module record
(IRX-12). The export table proves the relocation ran: its entries are stored as
`0x20, 0x28, 0x30, 0x38` and read back as `0x820, 0x828, 0x830, 0x838` once
loaded, each moved by the base, while the terminator stays zero (IRX-5b).

**Two modules now, and they call each other.** `LOADCORE` imports `sysmem`
ordinal 4 and its entry uses it, which is the first cross-module call in the
image and therefore the first real test of IRX-9's binding:

```
libraries: sysmem v1.01 @0x8c0, loadcore v1.01 @0xa44
imports  : sysmem @0xa90 bound
loadcore's allocation: 0x100000
```

The loader binds a module's imports before entering it and registers its
exports after relocating it; `SYSMEM`'s bump allocator answers with the heap
start, which also proves `SYSMEM`'s own entry ran, since an uninitialised
cursor could not.

Marking that import table unbindable — IRX-9b's low flag bits — makes the gate
say exactly what broke:

```
IRX-9: import tables ['sysmem'] were never bound
IRX-9: the cross-module call returned 0x4, want 0x100000
```

`0x4` is the ordinal: an unbound stub is `jr $ra; addiu $v0, $zero, 4`, so it
returns harmlessly with the ordinal still in `$v0`, which is IRX-8a's
survivability demonstrated rather than asserted.

**And the two processors meet.** `EESYNC` is last in the boot list and does
nothing but wait for the EE; the kernel's `sif.S` raises the flag it is waiting
for. Run together, each releases the other:

```sh
python3 tools/ps2sim.py build/rom.bin --traffic
```

```
MSCOM 0x800173c0  MSFLG 0x00010000     (the EE's to write)
SMCOM 0x00000b70  SMFLG 0x00010000     (the IOP's to write)
IOP: idle loop            EE: # The IOP answered; the SIF handshake is complete.
```

That is `spec/03` BOOT-10 on our own image. The asymmetry of BOOT-10c is the
part that had to be right, and the gate demonstrates why: swapping the EE's
raise from `MSFLG` to `SMFLG` — one halfword of one instruction — produces

```
BOOT-10a: the EE published MSCOM 0x800173c0 and MSFLG 0x0
BOOT-10d: the IOP did not reach an idle loop; it stopped at 0x00000b04
BOOT-10: the EE never got past its wait for the IOP
```

Neither side crashes. They wait for each other forever, which is exactly the
livelock BOOT-10c warns is the failure mode.

## Deviations from the reference, and why

**The scan resolves `RDRAM` by name.** `spec/04` EE-2 records that the
reference calls `0x9FC41000` — a hard-coded address — and EE-2a warns that a
build must either place the file at that offset or change the constant, because
the two must never drift. Our reset path resolves the name through the same
ARC-4 scan it already needs for `KERNEL`, so there is no constant to drift.
`tools/eesim.py` was changed to match: it takes the observation point for EE-2
from the image's own archive rather than assuming the reference's offset.

**The `KERNEL` copy moves words, not quadwords.** EE-3b describes `lq`/`sq`,
sixteen bytes an iteration. Four word loads and stores move the same bytes to
the same place; the R5900-only encodings are not required for the result, and
the assembler does not know them.

**The module container is produced, not hand-assembled.** `spec/02` IRX-1
wants an ELF with one relocatable load segment and its fixups intact, which a
linker discards by default. The build links each module at zero with
`--emit-relocs` and `tools/mkirx.py` rewrites the result: two program headers,
the `.iopmod` of IRX-2, and the `REL` entries filtered to the four types IRX-3
allows — refusing any other type rather than emitting a module no loader can
take. It writes the entry's `EXTINFO` from the same arguments, because IRX-2a
requires the two to agree.

**`IOPBOOT` is position-independent.** The reference is linked at the address
its archive offset gives it, and the archive keeps a padding entry to hold it
there (`spec/03` BOOT-7a). Ours computes its own base with a `bal` and uses
`bal` for every internal call, because `jal` encodes a *link-time* absolute
target and would jump into nothing once the file moves. No padding entry then
has to be kept in step with the layout.

**The exception dispatcher restores `$t9` through a stable base.** EE-6 quotes
the reference restoring it through a register the table lookup has already
overwritten. Ours keeps the base in `$k1`, so the restore reads the word it
saved. What EE-6c actually requires — no shift between the `0x7C` mask and the
index — is reproduced exactly.

**The loader registers a module's exports; the module does not.** In the
reference a module registers itself by calling `loadcore` ordinal 6 from its
entry (IRX-10a). Ours has the loader do it, because the first module is loaded
before any `loadcore` exists and would otherwise need a bootstrap path of its
own. `LOADCORE` still exports ordinals 6 and 10 with the same semantics, over
the same registry, for modules that register themselves the reference's way.

**The registry head is at a fixed address.** The reference keeps it inside
`LOADCORE`'s data. Ours is a word of low RAM shared between the boot block's
loader and `LOADCORE`, for the same reason: something has to own it before
`LOADCORE` is loaded.

**`SYSMEM`'s allocator only bumps.** It hands out memory and can give back only
the most recent allocation, refusing anything else rather than leaking
silently. The heap extent is a fixed range until the boot parameters of BOOT-4
step 5 are plumbed through; a real free list arrives with `HEAPLIB`.

**The syscall entry does not save the full context.** EE-7e's 128-bit `sq`
context save exists for the scheduler, which does not exist yet. The entry
preserves `$ra`, `$sp` and `$at`, and handlers clobber the temporaries. This is
a deviation that must close before the scheduler group is written, not one that
can stay.

**The bus-configuration table holds only its POST entry.** `spec/03` BOOT-4
step 1 applies a table of `(register, value)` pairs, and BOOT-5's first code is
emitted by one of those pairs. The remaining pairs configure the SSBUS and RAM
controllers with values the hardware dictates; they are not needed to boot an
emulator and belong with hardware bring-up. The table's structure, the
first-pair bit preservation and the POST side effect are all implemented.

## What is not built yet

`ninja -C build check` prints this list at the end of every successful run, so
it cannot quietly go stale:

- loading an IRX module: `IOPBOOT` locates them but cannot yet relocate, link
  or enter one (`spec/02`)
- 111 of the 125 syscall slots, which resolve to the reporter rather than to
  their own handlers (`spec/05` SYS-1)
- EE-7e's context save, and the scheduler that needs it
- the SIF as a data path: the two meet, but move no data, so `spec/04` EE-9's
  boot tail across it is out of reach

## How the image is judged

`tools/imgcheck.py` is the build's own gate, and it is deliberately *stated*
rather than lenient: it asserts what the image claims to do at this milestone
and fails if any of it stops holding. As components land, its expectations
tighten until the reference gates — `iopsim.py --check`, `eesim.py --check`,
`ps2sim.py --check`, `irxinfo.py --check`, `eeksys.py --check`,
`eeabi.py --check` — can be run against our image on the same terms as the
reference's.
